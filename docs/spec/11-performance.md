# 11. 性能目標と予算

## 1. 目標

| 項目 | 必達 | 目標 |
|---|---|---|
| エージェント数 | 20,000 | 50,000 |
| シミュレーション | 20 Hz を実時間 1x で維持（20,000 体） | 50,000 体で 4x 早送り |
| 描画 | 60 fps @ 1080p（20,000 体） | 60 fps @ 1080p（50,000 体） |
| メモリ（wasm ヒープ） | 300 MB 以下 | 200 MB 以下 |
| 初回ロード | 5 MB 以下 | 3 MB 以下 |
| 地形生成（5 km, Normal） | 3 秒以下 | 1.5 秒以下 |
| 会戦の初期化（50,000 体の生成） | 2 秒以下 | 1 秒以下 |

対象環境の下限: 2020 年以降のノート PC（4 コア、統合 GPU）、Chrome / Firefox / Safari。
モバイルは対象外だが、L2 以下の観戦だけなら動く程度を目指す。

## 2. メモリ予算

### 2.1 兵士（50,000 体）

| 配列群 | バイト/体 | 合計 |
|---|---|---|
| ホット（pos, vel, facing, state, flags） | 16 | 800 KB |
| ウォーム（hp, fatigue, morale, unit_id, target, slot, think_at, z） | 20 | 1.0 MB |
| コールド（attrs, equip, archetype, horse, name_seed） | 28 | 1.4 MB |
| 知覚キャッシュ（neighbors 等） | 32 | 1.6 MB |
| 判断ログ（直近 3 件 × スコア内訳） | 24 | 1.2 MB |
| **合計** | **120** | **6.0 MB** |

**1 体 128 バイト以下**を守る。ホットが 16 バイトに収まっているので、
64 バイトのキャッシュラインに 4 体分の位置情報が乗る。移動と衝突の
ループでこれが効く。

### 2.2 その他

| 対象 | サイズ |
|---|---|
| 地形グリッド（5 km、2 m セル） | 45 MB |
| 空間ハッシュ | 6.3 M セル × 4 B + 50 K × 4 B = 25 MB |
| 馬（5,000 頭） | 100 KB |
| Projectile（最大 8,000） | 300 KB |
| CommandNode（500 ノード、Blackboard 込み） | 2 MB |
| Structure・攻城兵器 | 500 KB |
| 巻き戻しスナップショット（10 個 × 圧縮後 2 MB） | 20 MB |
| **合計** | **約 100 MB** |

地形グリッドが最大の消費者。8 km マップにする場合はセルを 4 m に落として
同程度に抑える。

### 2.3 空間ハッシュの縮小

6.3 M セルの `cell_start` 配列（25 MB）は無駄が大きい。兵士がいるのは
戦場のごく一部なので、**アクティブ領域だけを覆う可変オフセットのグリッド**にする。

```
アクティブ矩形 = 全兵士の bounding box + マージン
典型的には 1.5 km × 1 km = 750 × 500 = 375,000 セル = 1.5 MB
```

矩形は毎 tick 再計算する（O(n) の min/max、安い）。これで 25 MB → 2 MB。

## 3. 計算量の予算

20 Hz、1 tick = 50 ms のうち、**シミュレーションに使える予算は 12 ms**
（実時間 1x で余裕を持たせ、4x 早送りに耐えるため）。

50,000 体での見積り:

| フェーズ | 回数 | 単価 | 予算 |
|---|---|---|---|
| 空間ハッシュ再構築 | 50,000 | 6 ns | 0.3 ms |
| 知覚更新（LOD、平均 2 Hz） | 5,000 / tick | 300 ns | 1.5 ms |
| 兵士 AI（平均 194,000 / 秒 = 9,700 / tick） | 9,700 | 2 µs | ← **19 ms 超過** |
| Unit AI（500 Unit × 3 Hz = 75 / tick） | 75 | 20 µs | 1.5 ms |
| 指揮官 AI（100 ノード × 0.5 Hz = 2.5 / tick） | 2.5 | 200 µs | 0.5 ms |
| 白兵戦解決 | 交戦中 7,500 | 200 ns | 1.5 ms |
| 弾道更新 | 4,000 | 100 ns | 0.4 ms |
| 移動積分 | 50,000 | 40 ns | 2.0 ms |
| 衝突解決（2 反復 × 12 近傍） | 50,000 × 24 | 8 ns | 9.6 ms |
| 士気 | 9,700 | 400 ns | 3.9 ms |
| 疲労・集計 | 50,000 | 15 ns | 0.75 ms |

**この見積りは予算を超える。** 対策が要る。

### 3.1 兵士 AI を 2 µs → 500 ns に

ユーティリティ AI で 12 候補すべてを評価すると重い。

- **候補の事前フィルタ**: 状態から明らかに不可能な行動を除外する
  （交戦していないのに `AttackTarget` を評価しない、矢がないのに `Shoot` を
  評価しない）。実際に評価するのは平均 3〜4 候補
- **スコアの部分計算をキャッシュ**: `threat_local` や `friendly_density` は
  知覚更新で計算済み。AI では読むだけ
- **整数演算のみ**、分岐を減らす、係数はローカルにコピーして間接参照を避ける

目標 500 ns なら 9,700 × 500 ns = **4.9 ms**。

### 3.2 衝突解決を 9.6 ms → 3 ms に

最大の消費者。

- **sleeping**: 速度がほぼゼロで、周囲も静止している兵士を除外する。
  会戦の大半の時間、後方の予備部隊（全体の 30〜50%）は静止している。
  → 実効 25,000〜35,000 体
- **近傍上限を密度で可変に**: 疎な場所では 4 近傍で十分。密集した前線でのみ 12
- **1 反復に減らす**: 密集時のみ 2 反復。多少の重なりは押し合いの表現として許容
- **SIMD**: wasm SIMD128 で 4 体分の距離判定を同時に。整数 SIMD が使える

目標 3 ms。

### 3.3 士気を 3.9 ms → 1.5 ms に

近傍の平均士気を毎回計算するのが重い。

- **セル単位で集計**: 空間ハッシュのセルごとに「平均士気」「敗走者数」を
  1 回だけ集計し（50,000 回の加算 = 0.5 ms）、各兵士はそのセルの値を読む。
  個別の近傍平均より粗いが、伝播の挙動としては十分
- セル集計は前 tick の値を使ってよい（1 tick の遅れは知覚できない）

### 3.4 修正後の予算

| フェーズ | 予算 |
|---|---|
| 空間ハッシュ | 0.3 ms |
| 知覚 | 1.5 ms |
| 兵士 AI | 4.9 ms |
| Unit / 指揮官 AI | 2.0 ms |
| 白兵戦 | 1.5 ms |
| 弾道 | 0.4 ms |
| 移動積分 | 2.0 ms |
| 衝突解決 | 3.0 ms |
| 士気 | 1.5 ms |
| 疲労・集計 | 0.75 ms |
| **合計** | **17.9 ms** |

まだ 12 ms を超えている。したがって:

- **50,000 体で実時間 1x**（1 tick = 50 ms の予算に対して 17.9 ms なので余裕あり）
  → 実時間 1x は達成できる。2x（25 ms 予算）も可能
- **4x 早送り（12.5 ms 予算）には届かない** → M9 のマルチスレッド化が必要
- **20,000 体なら約 7 ms** → 4x 早送りまで単一スレッドで達成

したがって当面の現実的な目標は:

| 体数 | 単一スレッドで達成できる速度 |
|---|---|
| 20,000 | 1x 〜 4x |
| 50,000 | 1x 〜 2x |

M9 でワーカー 4 並列にすれば 50,000 体で 8x まで届く見込み。

## 4. マルチスレッド化の設計（M9）

`wasm-bindgen-rayon` + `SharedArrayBuffer`。COOP/COEP ヘッダの配信が前提。

並列化しやすい順:

| フェーズ | 並列化 | 方法 |
|---|---|---|
| 衝突解決 | ◎ | 空間を帯に分割。境界の兵士のみ最後に逐次処理 |
| 移動積分 | ◎ | 完全に独立。単純な chunk 分割 |
| 兵士 AI | ◎ | 読み取り専用の入力 → 出力配列に書くだけ |
| 知覚 | ◎ | 同上 |
| 士気（セル集計） | ○ | 集計は並列リダクション、適用は独立 |
| 白兵戦 | △ | ダメージの書き込みが競合する。原子加算か、ダメージイベントを集めて後で適用 |
| 空間ハッシュ | ○ | 並列カウントソート |
| Unit / 指揮官 AI | × | 数が少ないので逐次のままでよい |

**決定論を保つための規約**（02 章で既に定めたもの）が、そのまま並列化を可能にする。

- エンティティ由来の RNG ストリーム → 実行順序に依存しない
- 読み書きフェーズの分離 → データ競合が起きない
- 白兵戦のダメージは `Vec<DamageEvent>` に積み、フェーズ末に **ID 順にソートして**
  適用する。並列に集めても適用順が決定的になる

## 5. 描画の予算

08 章 8 節を参照。要点のみ:

| パス | 予算 |
|---|---|
| 地形チャンク | 2 ms |
| 人物ポリゴン生成・転送 | 3 ms |
| その他 | 5 ms |
| **合計** | **10 ms** |（16.6 ms のうち）

人物ポリゴンVBOの更新が最大の懸念。Wasm側の画面外カリングで、ズームイン時は
大半を形状生成前に除外する。L0/L1で密集しすぎた場合は形状を自動簡略化し、
最悪ケース（L3/L4で全体を見る場合）は決定論的な間引きで対応する。

## 6. 計測とリグレッション

`sim-headless` にベンチモードを持たせ、CI で毎回計測する。

```bash
cargo run -p sim-headless --release -- bench \
    --scenario data/scenarios/bench_50k.toml \
    --ticks 2000 --report json
```

出力:

```json
{
  "soldiers": 50000,
  "ticks": 2000,
  "total_ms": 34210,
  "ms_per_tick": 17.1,
  "phases": {
    "spatial_hash": 0.28, "perception": 1.44, "soldier_ai": 4.71,
    "collision": 2.93, "morale": 1.38, "melee": 1.52, "movement": 1.98
  },
  "max_tick_ms": 24.8,
  "state_hash": "0x8A3F..."
}
```

CI は以下で失敗する。

- `ms_per_tick` が基準値の **+10%** を超えた（性能リグレッション）
- `state_hash` が前回と変わった（意図しない挙動変化。データ変更時は基準を更新する）
- `max_tick_ms` が 40 ms を超えた（スパイクは体感に直結する）

ネイティブと wasm で 2 回走らせ、`state_hash` の一致も確認する。

## 7. 段階的な負荷試験

M2 の時点から継続的に測る。

| マイルストーン | 体数 | 測定内容 |
|---|---|---|
| M2 | 5,000 | 移動・衝突のみ。60 fps を維持できるか |
| M4 | 20,000 | 戦闘込みで 1x が回るか |
| M6 | 20,000 | 工兵・地形改変込み |
| M9 | 50,000 | 全機能、マルチスレッド、4x |

**早い段階から実際の体数で測る**。「後で最適化する」は SoA のレイアウトや
空間索引の選択をやり直す羽目になる。M2 で 5,000 体が回らないなら、
その時点で設計を見直す。
